# ui-design

이 스킬은 **절차**만 담는다. 토큰 이름·색 값·컴포넌트 규약 같은 사실은 프로젝트의 `DESIGN.md`와 `tokens.css`가 원본이다. 여기에 복사하지 않는다.

## 0. 전제

프로젝트 루트에 `DESIGN.md`가 있어야 한다. 없으면 UI 작업을 시작하지 말고 이렇게 답한다:
> "이 프로젝트에 DESIGN.md가 없습니다. ui-skill-set 설치(README의 수동 설치 6단계, 또는 `/ui-init`) 후 진행할게요."

## 1. 읽기 (코드 전, 항상)

1. `DESIGN.md` 전체를 읽는다. frontmatter의 `mode_default`, `dials`, `gradient_policy`, `radius_scale`, §8 예외 표를 특히 본다.
2. `tokens_path`의 토큰 파일에서 **semantic 이름**을 확인한다 (`--{prefix}-color-{fg|bg|stroke}-…`, `--{prefix}-radius-{control|card|sheet}`, `--{prefix}-shadow-1…3`, `--{prefix}-duration-*`, `--{prefix}-ease-*`). Tailwind면 `@theme` 블록의 유틸리티 이름.
3. 이미 있는 화면 하나를 연다. 기존 패턴(버튼, 카드, 폼)이 있으면 그것이 기준이다. 새로 발명하지 않는다.

## 2. 디자인 리드 (한 줄 선언)

코드를 쓰기 전에 **정확히 한 줄**로 선언한다:

> 읽기: `<화면>` · 모드 **`<Operate|Persuade|Read|Experience>`** · 대상 `<누구, 어떤 상황>` · 다이얼 V/M/D `<n/n/n>`

- 모드는 **화면 단위**로 고른다. 제품 화면은 Operate. 랜딩·가격표만 Persuade. 문서·도움말은 Read. 갤러리·포트폴리오는 Experience. 도구의 랜딩도 Persuade이고, 브랜드 회사의 문서도 Read다.
- 다이얼은 DESIGN.md 기본값을 쓴다. Persuade일 때만 +2까지 올릴 수 있다.
- 브리프가 두 갈래로 읽히면 질문을 **딱 하나** 한다. 확신이 서면 묻지 않고 선언 후 진행한다.

| 모드 | 방문자의 성공 | 우선순위 |
|---|---|---|
| Operate | 과업을 끝낸다 | 스캔 가능성, 일관성, 예측 가능한 컨트롤. 브랜드는 디테일에만 |
| Persuade | 결정하고 행동한다 | 첫 화면의 가치 제안, CTA 1개, 실제 이미지 |
| Read | 이해한다 | 구조, 측정폭, 행간, 머무를 만한 읽기 경험 |
| Experience | 작품 안에 있다 | 작품이 앞, 인터페이스는 뒤로 |

## 3. 만들기

편집 직전에 `references/craft-floor.md`를 로드한다 (계획만 할 때는 로드하지 않는다). 한국어 텍스트가 있으면 `references/korean-typography.md`도. 필요할 때 더 로드한다:
- `references/banned.md` — 금지 항목 전체와 각각의 예외 조건. "이거 써도 되나" 판단이 설 때.
- `references/states-and-a11y.md` — 상태 5종·대비·키보드·터치·스크린리더. 인터랙티브 컴포넌트나 폼을 만들 때.

규칙 요약 (본문은 references):
- **토큰만.** 원색·`font-family` 직접 지정·Tailwind 기본 팔레트 클래스는 훅이 차단한다. 차단되면 우회하지 말고 토큰으로 고친다.
- **액센트 1색, 라디우스 스케일 1종, 그림자 ≤ 3개 요소.** DESIGN.md §2, §5.
- **상태 5종을 같이 만든다**: hover · disabled · loading(스켈레톤) · error · empty. "성공 상태만"은 미완성이다.
- **CTA는 화면당 1개.** 같은 의도의 버튼을 두 개 두지 않는다.
- **아이콘은 라이브러리 1종**, 이모지·유니코드 글리프는 아이콘이 아니다.
- **카드는 계층이 필요할 때만.** 중첩 카드 금지. 간격과 구분선으로 묶는다.
- **모션은 동기가 있어야 한다.** 한 문장으로 "이 움직임이 무엇을 알려주는가"에 답 못 하면 뺀다.
- **실제 카피.** 로렘 입숨·"홍길동"·완벽한 숫자(99.9%) 금지. 성공 메시지에 느낌표 없음, 에러에 "앗!" 없음.
- UI 파일은 Edit/Write 도구로 쓴다. Bash 리다이렉트로 쓰면 훅을 우회하게 되므로 금지.

## 4. 점검 (한정된 패스)

1. 다 만든다. 중간에 멈춰서 스크린샷·셀프 QA를 반복하지 않는다.
2. `references/preflight.md`를 한 번 훑고, 걸리는 것을 **한 번에** 고친다.
3. 필요하면 한 번 더 확인하고 끝낸다. 세 번째 패스는 없다. 종료 시 `design-lint --stop`이 하드 룰을 한 번 더 본다.
4. 훅이 "위반 0건"이라고 해도 좋은 디자인이라는 뜻은 아니다. 탐지기는 결함의 증거이지 품질의 증명이 아니다.

## 5. 브리프가 이긴다

사용자가 명시적으로 요구한 것(특정 색, 그라데이션, 폰트, 스타일)은 이 스킬의 기본값보다 우선한다. 다만:
1. 그것이 하드 룰에 걸리면 **먼저 한 줄로 확인**한다: "DESIGN.md 정책상 기본 금지입니다. 예외로 기록하고 진행할까요?"
2. 승인되면 해당 파일에 `/* ui-lint-allow <rule>: <이유> */`를 넣고 DESIGN.md §8 표에 한 줄 추가한다.
3. 이유 없는 마커, 훅 비활성화, 토큰 파일 밖의 원색 추가는 승인이 있어도 하지 않는다. 대신 토큰 파일에 토큰을 추가한다.

## 6. 하지 않는 것

- DESIGN.md를 무시하거나 임의로 고치기 (§8 예외 표 제외)
- 새 아이콘 라이브러리·폰트·색 램프를 묻지 않고 추가하기
- 한 화면에서 라이트/다크 섹션을 섞기
- "나중에 채움" 플레이스홀더 컴포넌트, div로 만든 가짜 스크린샷
- 이 문서에 없는 스타일 판단을 "취향"으로 내리기. 근거는 DESIGN.md 아니면 사용자 브리프다.
